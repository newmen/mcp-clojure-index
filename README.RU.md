# MCP Clojure Code Index

MCP-сервер, который позволяет LLM-агенту получать точные и компактные ответы на вопросы о кодовой базе на Clojure: где определено то или иное имя, кто его использует, что содержит namespace, каков исходный код конкретного определения (Definition), какие существуют реализации (Implementations) протокола или мультиметода и, опционально, где находится код, выполняющий определённое действие.

## Назначение

LLM-агенты тратят большую часть своих токенов на изучение кода: сначала выполняют `grep`, а затем читают файлы, чтобы разобраться, что именно представляет собой каждое найденное совпадение.

Этот сервер отвечает на вопросы вроде «где определён X», «кто использует X», «что содержится в этом namespace» и «где находится код, выполняющий Y», предоставляя **компактные ответы** (одна строка на каждую найденную сущность, с жёстким ограничением размера), которые при этом **полнее результатов `grep`**.

Сервер находит использования через любые alias, `:refer`, `#'var`, `with-redefs`, функции, переданные в качестве значений, а также keywords в исходном коде и EDN-файлах.

Если ответ когда-либо оказывается объёмнее или менее точным, чем результат `grep`, это считается ошибкой.

Принципы проектирования описаны в `docs/adr/`, терминология — в `GLOSSARY.md`.

## Сколько экономит

**На вопросах о коде — около 90% токенов** по сравнению с базовыми инструментами Claude (Grep и чтение файлов). **За всю сессию экономия в среднем около 12–15%** всех токенов.

| Что спрашивает агент | Инструмент | Базовые инструменты | С сервером | Экономия |
|---|---|---|---|---|
| Где определён X, с arglists, Type signature¹ и Docstring summary | `find_definition` | ~2 100 токенов | ~75 токенов | **96%** |
| Исходный код X | `get_source` | ~1 600 токенов | ~110 токенов | **93%** |
| Кто использует X | `find_usages` | ~9 600 токенов | ~130 токенов | **99%** |
| Где код, который делает Y | `semantic_search` | ~17 000 токенов | ~390 токенов | **98%** |
| Что есть в namespace | `namespace_summary` | ~840 токенов | ~250 токенов | **71%** |
| **Вся рабочая сессия** | | | | **~12–15%** |

¹ Если в конфиге задан `:doc/signature` (см. [Настройка](#2-настройка)); в обоих измеренных проектах он задан.

Сессия экономит меньше, потому что навигация — лишь её часть: в 123 реальных сессиях Claude Code на двух проектах grep и чтение кода, который потом не правился, заняли 16% входящих токенов (13% в медианной сессии); системный промпт, рассуждения, правки и запуск тестов стоят столько же с сервером и без него. Кроме того, ответы точнее: на каждый вопрос «кто использует X» grep приносил 7–10 строк, которые не являются использованиями.

Как измеряли: по 20 случайно выбранных функций в двух проектах (этот репозиторий и приложение на 220 файлов), все namespace и по 12 написанных вручную вопросов «где код, который делает Y»; база — то, что делает Claude Code без сервера: grep, затем 42% файлов читаются целиком, остальные — фрагментами (доля посчитана по его транскриптам). Даже против идеального агента, который ищет точным шаблоном и читает только нужные строки, сервер экономит 50–98% на каждом вопросе, кроме `namespace_summary`: тот получается того же размера, но вдобавок даёт arglists, Type signatures, спеки и список namespace, которые его требуют. **Цифры меняются от проекта к проекту**: они растут с размером файлов и с тем, насколько часто повторяются имена. Методика, цифры по каждому проекту и команды для замера своего проекта — в [ADR-0009](docs/adr/0009-measuring-savings-against-grep.md).

## Возможности

- **Определения на основе анализа clj-kondo** — vars, macros, тесты (`deftest`), multimethods и их методы, specs (`s/def`), protocols, records, а также формы проектных макросов, объявленных через `lint-as` в `.clj-kondo/config.edn` проекта.
- **Поиск использований полнее, чем `grep`** — aliases, `:refer`, `#'var`, функции, переданные в качестве значений, `with-redefs`, формы `comment`, `:require`, keywords в исходном коде и в файлах `.edn`.
- **Ограничение объёма вывода (Output budget)** — каждый ответ содержит одну строку на найденную сущность, с жёсткими ограничениями по количеству строк и символов; поддерживается постраничная выдача с помощью `offset`.
- **Актуальность данных (Freshness)** — файлы, изменённые на диске, анализируются повторно перед каждым ответом; индексация embeddings догоняет изменения в фоновом режиме.
- **Qdrant и Ollama необязательны** — они нужны только для `semantic_search`; все остальные инструменты работают без них.

## Требования

- [Java](https://adoptium.net/) 21+
- [Leiningen](https://leiningen.org/) 2.11+ (только для разработки и сборки)
- Только для `semantic_search` (опционально):
  - [Qdrant](https://qdrant.tech/) — векторная база данных.
  - [Ollama](https://ollama.com/) с моделью `bge-m3` — для создания многоязычных embeddings.
  - Опционально reranker: `llama.cpp` с командой `llama-server --rerank` и моделью `qllama/bge-reranker-v2-m3` — точно сортирует найденные результаты и присваивает им оценку релевантности.

Модели по умолчанию многоязычные: запросы на русском или английском (и ещё более чем на 100 языках) находят docstrings, написанные на любом из них. Альтернатива для кода, документированного по-английски, описана в разделе [Выбор моделей](#choosing-the-models).

Если Qdrant или Ollama недоступны, сервер всё равно запускается, и все инструменты точного поиска продолжают работать. При этом `semantic_search` сообщает, что он недоступен.

Без reranker функция `semantic_search` также работает: результаты сортируются на основе объединения векторного поиска и поиска по словам в именах и docstrings. При этом оценка релевантности не возвращается.

### 1. Установка и запуск необязательных зависимостей (только для семантического поиска)

<details> <summary><b>Qdrant</b> — векторная база данных</summary>

```bash
docker run -d -p 6333:6333 --name qdrant qdrant/qdrant
```

Проверка:

```bash
curl http://localhost:6333/collections
```

</details>

<details> <summary><b>Ollama</b> — модель для создания embeddings</summary>

```bash
ollama pull bge-m3
```

</details>

<details> <summary><b>Reranker</b> (опционально) — llama-server с моделью bge-reranker-v2-m3</summary>

Ollama не может самостоятельно запускать модель reranking (у неё нет API для reranking), однако может скачать эту модель. В Linux-сборки Ollama входит `llama-server`, который можно использовать следующим образом:

Bash:

```bash
ollama pull qllama/bge-reranker-v2-m3
MODEL=$(ollama show --modelfile qllama/bge-reranker-v2-m3 | sed -n 's/^FROM //p')
LD_LIBRARY_PATH=/usr/local/lib/ollama /usr/local/lib/ollama/llama-server -m "$MODEL" --rerank --port 8012
```

Fish:

```
ollama pull qllama/bge-reranker-v2-m3
set MODEL (ollama show --modelfile qllama/bge-reranker-v2-m3 | sed -n 's/^FROM //p')
LD_LIBRARY_PATH=/usr/local/lib/ollama /usr/local/lib/ollama/llama-server -m "$MODEL" --rerank --port 8012
```

Любой `llama-server` из проекта [llama.cpp](https://github.com/ggml-org/llama.cpp) работает аналогичным образом.

Проверка:

```bash
curl http://localhost:8012/health
```

Сервер отвечает той моделью, с которой был запущен, независимо от `:reranker/model`: после смены модели его нужно перезапустить.

</details>

<details id="choosing-the-models"> <summary><b>Выбор моделей</b> — многоязычные (по умолчанию) или для кода</summary>

| | Многоязычные (по умолчанию) | Для кода |
|---|---|---|
| `:ollama/embedding-model` | `"bge-m3"` (1,2 ГБ, 1024 измерения) | `"vishalraj/nomic-embed-code"` (49 МБ, 768 измерений) |
| `:reranker/model` и файл модели llama-server | `"qllama/bge-reranker-v2-m3"` (635 МБ) | `"qllama/bce-reranker-base_v1"` (303 МБ) |
| Docstrings и запросы | на любом языке, измерены русский и английский | на английском |

Выбирайте многоязычные модели, если docstrings или запросы не на английском: с моделями для кода все результаты по русским docstrings получают почти одинаковую оценку, и нужное определение может не попасть в первую тройку. Модели для кода подходят проекту с docstrings на английском, когда важны память или время создания embeddings: на английских docstrings обе пары находят одни и те же определения. Измерения приведены в `docs/adr/0008-multilingual-models.md`.

Смена `:ollama/embedding-model` один раз заново создаёт embeddings всего проекта: коллекция Qdrant хранит имя своей модели и пересоздаётся, если оно другое, а кэш embeddings хранит отдельную директорию для каждой модели.

</details>

### 2. Настройка

`resources/config.edn` содержит конфигурацию по умолчанию.

Корневая директория проекта определяется следующим образом (в порядке приоритета):

1. Значение `:index/root-path`.
2. Переменная окружения `QD_PROJECT_ROOT` или `VSCODE_CWD`.
3. Текущая рабочая директория.

| Ключ                           | Значение по умолчанию                                                  | Описание                                                                                                                                                                                 |
| ------------------------------ | ---------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `:index/root-path`             | см. выше                                                               | Путь к индексируемому проекту                                                                                                                                                            |
| `:index/include-extensions`    | `[".clj" ".cljc" ".cljs" ".edn"]`                                      | Расширения файлов, подлежащих анализу                                                                                                                                                    |
| `:index/exclude`               | `[]`                                                                   | Директории, исключаемые из анализа. Директории `.calva`, `.claude`, `.clj-kondo`, `.cpcache`, `.git`, `.kilo`, `.lsp`, `.mcp`, `logs`, `target`, `tmp` всегда исключаются                |
| `:search/exclude`              | `[]`                                                                   | Исключения из поиска: пути (синтаксис как у `:index/exclude`), которые не попадают в `semantic_search` и не эмбеддятся, обычно сгенерированный код; точные инструменты их по-прежнему видят |
| `:output/limit`                | `50`                                                                   | Бюджет вывода: максимальное количество найденных сущностей в одном ответе. Параметр `limit` отдельного вызова может только уменьшить это значение                                        |
| `:output/max-chars`            | `4000`                                                                 | Бюджет вывода: максимальное количество символов в одном ответе                                                                                                                           |
| `:doc/signature`              | нет (Project config этого репозитория задаёт `{:strategy :last-paragraph}`) | Как найти сигнатуру типов в docstring: `:last-paragraph` (последний абзац docstring из двух и более абзацев) или `{:strategy :pattern :regex "..."}` (первая группа захвата регулярного выражения; выражение без неё отклоняется при запуске); без ключа или с `nil` сигнатур нет |
| `:qdrant/host`, `:qdrant/port` | `"localhost"`, `6333`                                                  | Адрес Qdrant (только для семантического поиска)                                                                                                                                          |
| `:qdrant/collection`           | Переменная окружения `QD_COLLECTION`, иначе `<project dir>-collection` | Имя коллекции Qdrant (только для семантического поиска)                                                                                                                                  |
| `:qdrant/recreate?`            | `false`                                                                | Удалить и заново создать коллекцию при запуске (только для семантического поиска)                                                                                                        |
| `:ollama/url`                  | `"http://localhost:11434/v1"`                                          | Адрес API Ollama (только для семантического поиска)                                                                                                                                      |
| `:ollama/embedding-model`      | `"bge-m3"`                                                             | Модель для создания embeddings (только для семантического поиска); при смене коллекция пересоздаётся                                                                                     |
| `:reranker/url`                | `"http://localhost:8012/v1"`                                           | Адрес reranker — API `/v1/rerank`, например `llama-server --rerank` (только для семантического поиска, опционально)                                                                      |
| `:reranker/model`              | `"qllama/bge-reranker-v2-m3"`                                          | Имя модели, передаваемое reranker (только для семантического поиска)                                                                                                                     |
| `:search/top-k`                | `100`                                                                  | Количество кандидатов, получаемых отдельно из векторного поиска и поиска по словам, а также количество объединённых кандидатов, передаваемых reranker (только для семантического поиска) |
| `:search/re-rank-top`          | `10`                                                                   | Количество результатов, оставляемых после reranking (только для семантического поиска)                                                                                                   |
| `:search/min-relevance`        | `0.3`                                                                  | Если лучшая релевантность ниже этого порога, `semantic_search` ставит перед результатами строку `no confident matches (best 0.15), try rephrasing in the docstrings' words` (и ` (they are mostly in Cyrillic)`, если большинство описаний написано одной нелатинской письменностью); подобран для `qllama/bge-reranker-v2-m3` (ADR-0008), для reranker, который даёт посторонним текстам более высокие оценки, порог нужно поднять (только для семантического поиска, нужен reranker) |
| `:embedding/cache-dir`         | `<root>/.mcp/embedding-cache`                                          | Директория кэша embeddings (только для семантического поиска)                                                                                                                            |

Если ответ достигает установленного Output budget, в его конце добавляется уведомление об усечении. Например:

`truncated: shown 50 of 120, pass offset=50 or narrow the query`

Это означает, что показано 50 результатов из 120. Чтобы получить следующие результаты, нужно передать `offset=50` либо сузить запрос.

#### Project config

Конфиг, переданный при запуске (конфиг сервера), задаёт значения по умолчанию для всех проектов. Проект может хранить свои настройки в Project config: файле `.clojure-index.edn` в корне проекта (`:index/root-path`), который коммитится вместе с проектом. Файл необязателен; без него конфиг сервера применяется как есть. См. ADR-0010.

- **Ключи.** Допустим любой ключ из таблицы выше. Ключ, которого не может быть в конфиге сервера (опечатка вроде `:search/exlude`), — ошибка, а не молча игнорируемое значение.
- **Замена.** Значение заменяет значение конфига сервера целиком; списки не объединяются, так что проект, которому нужны и элементы `:index/exclude` сервера, повторяет их. Всегда исключаемые директории добавляются к `:index/exclude` в любом случае. Шаблоны `:index/exclude` и `:search/exclude` — регулярные выражения, которые ищутся в пути относительно корня проекта; `.` в них совпадает только с точкой.
- **Горячие ключи** применяются со следующего ответа: перед каждым вызовом инструмента сервер сверяет mtime (и наличие) файла, как и для исходников. Это `:index/include-extensions`, `:index/exclude`, `:search/exclude`, `:search/min-relevance`, `:output/limit`, `:output/max-chars` и `:doc/signature`. При смене `:index/exclude` или `:index/include-extensions` новые исключённые файлы убираются из индекса, а новые включённые анализируются; при смене `:search/exclude` embeddings новых исключённых файлов удаляются, а снова включённые эмбеддятся в фоне. Удаление файла возвращает значения конфига сервера.
- **Холодные ключи** — все остальные (Qdrant, Ollama, reranker, транспорт, `:search/top-k`, `:search/re-rank-top`, `:qdrant/collection`, `:embedding/cache-dir`, …). Они читаются только при запуске сервера. Пока значение такого ключа в файле отличается от действующего, ответы заканчиваются строкой `.clojure-index.edn: :search/top-k changes after a server restart` (одна строка со всеми такими ключами).
- **Ошибки.** Нечитаемый или некорректный файл не останавливает сервер: он продолжает работать на прежних настройках, а пока файл сломан, ответы начинаются со строки `project config error in .clojure-index.edn: <причина>; using previous settings`. Если файл некорректен с самого запуска, сервер работает только на конфиге сервера и сообщает об ошибке той же строкой. Некорректный конфиг сервера по-прежнему останавливает сервер при запуске, и сообщение называет его абсолютный путь.

Агент может сам редактировать Project config; инструкции сервера ему об этом сообщают. Полный пример:

```clojure
{:index/exclude        ["dev" "test-resources"]          ; заменяет список сервера
 :search/exclude       ["com/google/protobuf" "^src/gen/"] ; сгенерированный код, убирается только из semantic_search
 :search/min-relevance 0.4
 :output/limit         30
 :doc/signature        {:strategy :last-paragraph}
 :search/top-k         50}                                ; холодный ключ: применится после перезапуска
```

### 3. Сборка uberjar

Перед первым запуском или после изменения исходного кода необходимо собрать исполняемый JAR:

```bash
lein uberjar
```

### 4. Запуск сервера

```bash
java -jar target/mcp-0.1.0-SNAPSHOT-standalone.jar resources/config.edn
```

Сервер запускается в режиме STDIO и ожидает сообщения JSON-RPC 2.0.

При запуске он анализирует проект с помощью clj-kondo (результаты хранятся только в оперативной памяти) и в фоновом режиме вычисляет embeddings для Search units.

При последующих запусках embeddings пересоздаются только для файлов, изменившихся с момента их последней индексации.

Коллекция Qdrant старого формата удаляется и создаётся заново. Если коллекцию удалили или очистили во время работы сервера или заменили коллекцией другого формата, модели embeddings или размера векторов (вручную или другим экземпляром сервера), сервер замечает это при следующем обновлении embeddings или семантическом поиске и заново создаёт embeddings всех файлов. Два экземпляра с разными моделями embeddings на одной `:qdrant/collection` будут пересоздавать коллекцию друг друга; дайте им разные имена коллекций.

## Интеграция с Kilo Code

### Глобальная конфигурация (доступна из любого проекта)

Сервер запускается через uberjar, а не через `lein run`.

Это необходимо потому, что Kilo использует таймаут 30 секунд, тогда как `lein run` требует более 60 секунд на запуск JVM и Leiningen.

Чтобы избежать проблем с `PATH` при запуске из Kilo, для `command`, JAR-файла и `config.edn` необходимо использовать абсолютные пути.

Добавьте следующую конфигурацию в `~/.config/kilo/kilo.jsonc`:

```json
{
  "mcp": {
    "clojure-code-index": {
      "type": "local",
      "command": ["/usr/bin/java", "-jar", "/path/to/mcp/target/mcp-0.1.0-SNAPSHOT-standalone.jar", "/path/to/mcp/resources/config.edn"],
      "workingDirectory": "/path/to/mcp",
      "enabled": true,
      "timeout": 30000
    }
  }
}
```

Замените `/path/to/mcp` полным путём к локальной копии этого проекта, а `/usr/bin/java` — путём к используемому JDK.

### Локальная конфигурация (для отдельного проекта)

Создайте файл `kilo.json` в корневой директории проекта либо `.kilo/kilo.jsonc`:

```json
{
  "mcp": {
    "clojure-code-index": {
      "type": "local",
      "command": ["/usr/bin/java", "-jar", "/path/to/mcp/target/mcp-0.1.0-SNAPSHOT-standalone.jar", "/path/to/mcp/resources/config.edn"],
      "enabled": true,
      "timeout": 30000
    }
  }
}
```

### Проверка

После настройки перезапустите Kilo Code.

В интерфейсе появится MCP-сервер `clojure-code-index`.

После его включения Kilo автоматически обнаружит следующие 6 инструментов:

| Инструмент             | Описание                                                                                           |
| ---------------------- | -------------------------------------------------------------------------------------------------- |
| `find_definition`      | Поиск места, где определено имя                                                                    |
| `find_usages`          | Поиск всех использований одного или нескольких имён и/или keywords                                 |
| `namespace_summary`    | Сводная информация об определениях namespace и о том, какие namespace подключают его через require |
| `get_source`           | Получение исходного кода конкретного определения                                                   |
| `find_implementations` | Поиск реализаций протокола или мультиметода                                                        |
| `semantic_search`      | Поиск определений и записей EDN по смыслу (требуются Qdrant и Ollama)                              |

## Доступные MCP-инструменты

Это именно те инструменты, которые возвращаются методом `tools/list`.

Имена могут быть указаны в следующих форматах:

- Простое имя: `relative-path`.
- С указанием alias, как он записан в соответствующем namespace: `output/relative-path`.
- Полностью квалифицированное имя: `mcp.output/relative-path`.

Если имя неоднозначно, сервер возвращает список подходящих кандидатов.

Все инструменты, кроме `get_source`, поддерживают параметры:

- `limit` — ограничение количества результатов (может только уменьшать значение `:output/limit`).
- `offset` — количество пропускаемых результатов (для постраничной выдачи).

Все ответы соблюдают ограничения Output budget. Docstring summary в строках ответа — первое предложение docstring, за которым следует `(+N chars)`, если текст продолжается. Definition без docstring, например spec, описывается блоком строк комментария `;;` прямо над её формой (без пустой строки между ними): такой комментарий везде считается её docstring — в Docstring summary, `doc: "full"`, Type signature и `semantic_search`. Docstring важнее комментария, а у namespace учитывается только docstring. Перед каждым ответом индекс перечитывается из изменённых файлов (по mtime), поэтому правки видны сразу.

### find_definition

```text
Входные параметры:
  names (array of strings, обязательный) — имена: простые, квалифицированные
                               через alias или полностью квалифицированные;
                               `multi dispatch-value` для defmethod
                               (например, `area :circle`);
                               keyword для spec.
  doc ("summary" | "full", по умолчанию "summary")
  limit, offset — считают определения (Definition) по всем именам вместе

Ответ:
  Одна группа на каждое различное имя, как в `rg --heading`,
  между группами — пустая строка:
  имя, как оно передано, затем одна строка на каждое определение (Definition):
  path:line  kind  ns/name  [arglists]  Type signature  Docstring summary

  С doc "full": строка path:line  kind  ns/name  [arglists],
  затем весь docstring с отступом в два пробела
  (`  (no docstring)`, если его нет).
  Docstring длиннее Output budget обрезается, в конце —
  `truncated: docstring shown A of B chars`.
```

Ненайденное имя сообщает об этом в заголовке своей группы (`foo: not found (checked 214 files, including tests)`); неоднозначное — заголовком `ambiguous: N definitions named foo, pass a qualified name` и списком кандидатов. Остальные имена отвечают как обычно. Страница, начинающаяся внутри группы, повторяет её заголовок. Пустой список имён даёт ответ `no names given`.

Пример (`names: ["relative-path", "output/render"]`):

```text
relative-path
src/mcp/output.clj:60  defn  mcp.output/relative-path  [root-path file-path]  Maybe String -> String -> String  Returns ...

output/render
src/mcp/output.clj:110  defn  mcp.output/render  ...
```

### find_usages

```text
Входные параметры:
  targets (array of strings, обязательный) — имена и/или keywords
                                             (:k, :ns/k, ::k, ::alias/k)
  kinds (array of strings) — только следующие типы использований (Usage):
      call, value, var-ref, redef, in-comment, require, keyword, edn
      По умолчанию: все типы.
  include_tests (boolean, по умолчанию true)
  context (boolean, по умолчанию true) — добавлять к строке контекст (Usage context)
  warnings_only (boolean, по умолчанию false) — только использования с предупреждением
                                                (Usage warning)
  limit, offset

Ответ:
  Для каждой цели — заголовок `target: N usages`,
  затем одна строка на каждое использование (Usage);
  между целями — пустая строка:
  path:line:col  usage-kind  ns/enclosing-definition  context  warning
```

Контекст (Usage context) — до 80 символов строки исходника вокруг использования, серии пробелов схлопнуты; `…` отмечает обрезанный конец.

Предупреждение (Usage warning) завершает строку, если оно есть: `wrong arity: 3 args, takes 1|2` (`takes 2+` для varargs) — у вызова число аргументов не совпадает ни с одной арностью цели; у `require` целевого namespace — `unused`, если в файле не используется ни алиас, ни одно из имён `:refer` (вызов или значение через алиас, имя из `:refer`, `#'`, `::alias/kw`, полностью квалифицированное имя), и `unused refer: b, c`, если не используются только эти имена из `:refer`. Голый require и `:refer :all` не помечаются. `unused` — подсказка: использование внутри макроса или через `resolve` не видно.

Если ничего не найдено, сервер сообщает, что именно было проверено. Например:

`no usages of x (checked 214 files, including tests)`

Это означает, что использований `x` не найдено (проверено 214 файлов, включая тесты).

### namespace_summary

```text
Входные параметры:
  ns (string, обязательный) — полностью квалифицированное имя namespace
  detail (boolean, по умолчанию false) — добавить Docstring summary
  limit, offset

Ответ:
  Заголовок:
      ns name  path  Docstring summary

  Для каждого Definition (приватность — как в исходнике: `defn-  name`, `def  ^:private name`;
  собственные спеки namespace — как ::name):
      line  kind  name  [arglists]  Type signature
      (без Type signature, если её нет у Definition или в проекте)
      с detail: line  kind  name  [arglists]  Type signature  Docstring summary

  Последняя строка:
      required by: ns1, ns2, ...
      либо `none`, если namespace нигде не подключается
```

### get_source

```text
Входные параметры:
  name (string, обязательный) — простое, квалифицированное через alias
                                или полностью квалифицированное имя.
  limit, offset — применяются к строкам тела определения
                  (или к списку кандидатов, если имя неоднозначно).

Ответ:
  Заголовок вида `path:start-end`,
  затем исходный код ровно одного Definition.

  Если тело определения превышает Output budget,
  в конце добавляется уведомление об усечении.
  Чтобы получить оставшуюся часть, передайте offset.
  Одна строка длиннее Output budget обрезается, в конце —
  `truncated: source shown A of B chars`.
```

### find_implementations

```text
Входные параметры:
  name (string, обязательный) — протокол или мультиметод
  limit, offset

Ответ:
  Одна строка на каждую реализацию (Implementation):
  defrecord, deftype, extend-type, extend-protocol, reify, defmethod

  path:line  ns/type-or-dispatch-value  method
```

### semantic_search

```text
Входные параметры:
  query (string, обязательный) — описание того, что делает код,
                                 на естественном языке.
  include_tests (boolean, по умолчанию false) — искать также
                                 определения в Test paths.
  limit, offset

Поиск:
  embedding запроса → Qdrant top :search/top-k ─┐
  слова из имён и docstrings (BM25) ────────────┴→
  объединение рангов (reciprocal rank fusion) →
  reranker → top :search/re-rank-top

Ответ:
  Одна строка на каждый результат.
  Исходные тела функций не возвращаются.

  score  path:line  kind  ns/name  Docstring summary

  score — оценка релевантности от reranker в диапазоне 0..1.
          Не возвращается, если reranker недоступен.

  Если лучшая релевантность ниже :search/min-relevance,
  первой строкой идёт
  `no confident matches (best 0.03), try rephrasing in the docstrings' words`,
  а если большинство описаний написано одной нелатинской
  письменностью, к ней добавляется ` (they are mostly in <Script>)`.
  Без reranker такой строки не бывает.

  Пока выполняется индексация последних изменений,
  в конце ответа добавляется:
  `embeddings stale for N files`
```

Требуются Qdrant и Ollama. Если они недоступны, инструмент сообщает, что семантический поиск недоступен.

## Архитектура

```text
src/mcp/
├── server.clj         — точка входа, JSON-RPC через STDIO,
│                        проверка актуальности данных перед каждым вызовом инструмента
├── config.clj         — загрузка конфигурации
├── code_index.clj     — анализ проекта с помощью clj-kondo
│                        в оперативной памяти (Definitions, Usages)
├── usages.clj         — Usages и их типы
├── output.clj         — Output budget и вспомогательные функции
│                        для формирования компактных ответов
├── docstring.clj      — Docstring summary и стратегии Type signature
├── text.clj           — схлопывание пробелов и обрезка с многоточием
├── tool.clj           — реестр инструментов (multimethods spec/call)
├── tools.clj          — tools/list и tools/call
├── tools/             — отдельный namespace для каждого инструмента
├── search_units.clj   — Search units для семантического поиска
├── semantic_index.clj — фоновое создание embeddings для Search units
├── embeddings.clj     — embeddings через Ollama,
│                        reranking через сервер с API /v1/rerank
├── lexical.clj        — поиск по словам (BM25) в именах Search units и docstrings
├── qdrant.clj         — векторное хранилище (Qdrant HTTP API)
└── search.clj         — векторный поиск + поиск по словам,
                         объединение рангов и reranking
```

## Разработка

```bash
# Тесты (Qdrant и Ollama не требуются)
lein test

# Интеграционные тесты, которым нужны Qdrant и Ollama с моделями по умолчанию;
# тесту с русскими docstrings (acceptance case 12) и тесту строки
# `no confident matches` (case 13) нужен ещё и reranker, остальные проходят и без него
lein test :integration

# Статический анализ
clj-kondo --lint src test

# Сборка uberjar (после изменения исходного кода)
lein uberjar
```
