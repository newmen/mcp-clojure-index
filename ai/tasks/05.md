# Task 5. Building the dependency graph

## Description

It is necessary to build a dependency graph between all the project symbols based on the results of the source code analysis. For each semantic chunk, the list of called functions, the used namespaces, the references to protocols, the implementations of protocols, the usage of record/type, and other structural dependencies that can be extracted without executing the program should be determined. The graph is built separately from the vector index and is used during hybrid search, when expanding semantic search results, and when building LLM context. During indexing, the dependency information is **not written directly into the Qdrant payload**, but must be associated with the corresponding record via its unique identifier (`id`) or the `hash` field. This allows after getting results from Qdrant to quickly expand the found context with neighboring graph vertices without re-analyzing the source code.

For example, after forming the following payload in Qdrant:

```json
{
  "id": "c5cdbd3b",
  "text": "(defn create-user ...)",
  "language": "clojure",
  "namespace": "bank.user",
  "symbol": "create-user",
  "type": "function",
  "visibility": "public",
  "file": "src/bank/user.clj",
  "start_line": 81,
  "end_line": 120,
  "hash": "6d0b9d7..."
}
```

a separate record must exist in the dependency graph, for example:

```json
{
  "id": "c5cdbd3b",
  "calls": [
    "bank.validation/validate-user",
    "bank.persistence/save-user",
    "bank.events/publish-user-created"
  ],
  "uses_namespaces": [
    "bank.validation",
    "bank.persistence",
    "bank.events"
  ],
  "implements_protocols": [],
  "used_by": [
    "bank.api/create-user-handler",
    "bank.import/import-user"
  ]
}
```

When executing a query, the agent first gets the Top-N results from Qdrant, and then by the `id` (or `hash`) field it can query the dependency graph and automatically expand the context with the related definitions.

### Tools

- rewrite-clj
- rewrite-clj zipper API
- loom (or a custom graph implementation)

### Input

A collection of semantic chunks and the formed metadata of each chunk.

### Output

A dependency graph containing links between symbols, mapped to the Qdrant records by the `id` or `hash` field.

### Acceptance criteria

- a graph vertex is built for each definition;
- called functions are defined;
- used namespaces are defined;
- protocol implementations and uses (if any) are defined;
- no duplicate edges;
- each graph vertex is uniquely matched to the Qdrant record through `id` or `hash`;
- the graph can be used to expand results after semantic search;
- when a file is deleted, all edges and vertices belonging to the deleted file are removed from the graph (via `mcp.graph/remove-file!`).
