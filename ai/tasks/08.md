# Task 8. Incremental indexing

## Description

It is necessary to implement a mechanism for tracking file changes in the project. When a file changes, it is re-parsed, the old records are deleted, and new ones are loaded. The rest of the index remains unchanged. Indexing must work automatically without a full collection rebuild.

### Handling a file deletion

When a file is deleted from the file system:
- delete all the records from Qdrant belonging to the file (filter by the `file` field);
- delete all the symbols of the file from the symbol index;
- delete all the edges of the file from the dependency graph.

No parsing of the source code or embedding generation is required when deleting.

### Handling a file move (rename)

The Java WatchService generates a sequence of `ENTRY_DELETE` (for the old path) and `ENTRY_CREATE` (for the new path) events. The watcher should implement coalescing (a debounce window of ~100 ms) to merge the DELETE+CREATE pair into take a single move event:
1. If the file content is unchanged (hash matches) — only update the `file` field in Qdrant, the symbol index, and the graph.
2. If the content has changed — perform a full reindex like the modification case (delete by old path, parse by new path, load).

### Tools

- Java WatchService

### Input

File system events.

### Output

The current index.

### Acceptance criteria

- only the affected files change;
- deleted files are removed from the index — Qdrant, the symbol index and the graph contain no records from the deleted file;
- no full reindex occurs;
- changes appear after saving the file;
- a file move (rename) is handled as a single event without loss or duplication of index records.
