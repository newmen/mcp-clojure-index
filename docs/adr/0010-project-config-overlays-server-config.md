# Project config overlays the server config

One server config (`config.edn`, passed at start) serves every project, but some settings belong to one project: which paths are generated code to keep out of semantic search, how its docstrings state Type signatures, its Test paths and exclusions. They now live in a Project config, `.clojure-index.edn` at the project root, committed with the project. Any key of `config.edn` may appear there and replaces the server's value whole (lists are not concatenated); `config.edn` holds the defaults for every key, and the directories that are always excluded are added either way. We chose a file in the project over project-specific patterns in the shared `config.edn`, which would mix every project's paths in one file, and over detecting generated code automatically, which guesses where the project's owner, or its agent, knows.

The agent may edit the Project config itself, for example to add a Search exclusion, so it is re-read by mtime before every answer, like the sources (ADR-0005). Keys that only shape answers or the index (`:index/include-extensions`, `:index/exclude`, `:search/exclude`, `:search/min-relevance`, `:output/*`, `:doc/signature`) apply from the next answer; a changed exclusion re-indexes or re-embeds only the files it affects. Keys that set up connections or the collection (Qdrant, Ollama, reranker, transport, `:search/top-k`, `:search/re-rank-top`, `:qdrant/collection`, `:embedding/cache-dir`, `:index/root-path`) are read at start only: a change to one of them is not applied, and answers say that it needs a restart, because switching an embedding model under a running server would mean rebuilding the collection mid-session. An unreadable or invalid Project config does not stop the server: answers start with `project config error in .clojure-index.edn: <reason>; using previous settings` (the server config alone, when it was invalid from the start). An invalid `config.edn` still stops the server at start.
